# AI 写词与作曲第二版技术文档

本文依据已确定的第二版 PRD，给出三个可行方案。推荐方案二：AI 规划音乐，程序按规则生成音符。当前只做技术设计，不开始开发。

## 1. 已确定的范围

- 面向短视频创作者、音乐爱好者，先供自己验证。
- 输入预设主题、情绪、风格，故事描述选填；只支持中文。
- 一次生成三版歌词：故事叙述、情绪表达、意象表达。选择一版，用户手动编辑。
- 根据最新歌词生成一版 45～75 秒的音乐小样，含主歌、副歌和自然结尾。
- 钢琴演奏主旋律，简单和弦伴奏，无女声或其他演唱。
- 支持试听、暂停、进度拖动、重新生成、下载 MP3。
- 不加账号、付费、作品库、分享、专业编曲、乐谱或 MIDI 下载。

这些方案不依赖完整歌曲生成 API，也不需要 GPU。它们输出的钢琴小样能展示旋律、节奏和和弦，不能完整复现摇滚、电子、R&B 的制作质感。中文歌词与音符对应不等于已经验证真人演唱自然；尤其中文声调和旋律的关系仍需试唱检查。

## 2. 三个方案的比较

| 方案 | 谁决定音乐 | 成本特点 | 主要取舍 |
|---|---|---|---|
| 一：规则作曲 | 程序根据预设规则生成 | 歌词用文本模型，作曲无额外模型调用 | 最稳定、容易控制，但易有模板感 |
| 二：AI 规划＋规则作曲（推荐） | AI 选音乐方向，程序写具体音符 | 多一次简短文本模型调用 | 变化与可控性较均衡，需要设计少量音乐规则 |
| 三：AI 直接生成音符 | 文本模型输出完整乐谱数据 | 输出较长，修复与重试可能增加成本 | 自由度高，但合法数据不代表好听 |

“重新生成”都会改变随机种子或重新请求模型；不承诺每次都比上一版更好。比较成本应计算得到一版满意结果的总成本，而不是只算单次请求。

## 3. 方案一：规则作曲

### 3.1 技术选型

| 技术 | 用途及原因 |
|---|---|
| TypeScript＋React＋Vite | 单页输入、歌词编辑和播放器；前后端都使用同一语言，便于自己维护 |
| Node.js＋Express | 后端调用文本模型、管理生成任务和下载；API 密钥不进入浏览器 |
| Zod | 检查输入及歌词返回格式，防止缺字段或不是三版歌词 |
| Tonal | 查询音阶、和弦音、转调；减少自行处理音名和音程的错误 |
| @tonejs/midi | 把音符数据写成 MIDI，分别保存旋律与伴奏轨道 |
| SQLite（better-sqlite3） | 保存当前项目和任务状态，不依赖外部数据库 |
| FluidSynth＋钢琴 SF2 音源 | 将 MIDI 演奏成 WAV，提供真正的钢琴采样声音 |
| FFmpeg | WAV 转 MP3，并检查成品时长 |

这里的 @tonejs/midi 是 MIDI 文件工具，不需要在浏览器用 Tone.js 合成声音。前端统一播放已经生成的 MP3，保证试听与下载一致。

### 3.2 数据流

```text
用户输入 → 后端调用文本模型 → 三版歌词 → 用户选定并编辑
→ 固定风格规则＋歌词分句＋随机种子
→ 节奏、旋律、和弦 → 校验 → MIDI → FluidSynth → WAV
→ FFmpeg → MP3 → 浏览器试听与下载
```

规则示例：强拍优先使用当前和弦的音；旋律以相邻音移动为主；重复短动机；副歌提高音区或节奏密度；句尾留停顿；结尾落在稳定音上。变化来自原创节奏模板、旋律生成规则和随机种子，不从现有歌曲直接拼接旋律。

### 3.3 数据结构草图

共用项目和音符结构见第 6 节。本方案额外需要：

```text
StyleConfig {
  styleId, configVersion,
  allowedBpmRange, allowedModes,
  chordProgressionIds, rhythmPatternIds,
  melodyRange, chorusVariationRules
}
```

风格与情绪分别影响速度、调式、力度和节奏；不要把“悲伤必须小调”写成不可变规则。

### 3.4 优缺点与取舍

- 优点：作曲不调用模型；时间、节拍、音区容易控制；相同规则和种子可复现。
- 缺点：规则需要音乐知识，作品容易相似；故事内容主要影响歌词，对音乐的细腻影响较弱。
- 适用：先验证流程、希望少花钱并且愿意接受较朴素的小样。

### 3.5 大白话解释

像给程序一本“作曲食谱”：它知道每种风格用什么节奏、哪些音可以搭配，再根据歌词安排长短句。做出来比较稳，但食谱少了，几首歌会像同一家店的菜。

## 4. 方案二：AI 规划＋规则作曲（推荐）

### 4.1 技术选型

| 技术 | 用途及原因 |
|---|---|
| TypeScript＋React＋Vite | 单页交互；用原生 HTML audio 播放最终 MP3 |
| Python＋FastAPI | 后端接口与音乐处理；Python 便于操作 MIDI、验证数据和扩展音乐算法 |
| Pydantic | 定义歌词、音乐规划和任务格式，验证模型输出 |
| 文本模型适配层 | 生成三版歌词，以及简短的音乐规划；使用支持结构化输出的服务，具体服务待选型 |
| Python 标准库＋mido | 程序按音乐规则产生音符，mido 写 MIDI；避免同时引入多套时间表示 |
| SQLite＋本地文件目录 | 保存任务与生成输入，音频存在磁盘；自测阶段够用 |
| 独立 Python worker | 执行模型请求和音频渲染，不阻塞网页请求 |
| FluidSynth＋SF2、FFmpeg | 统一渲染钢琴音频并输出 MP3 |

后端和 worker 放在同一台本地电脑或普通服务器上即可。首版只启动一个 worker，不引入 Redis、Celery、GPU 或容器集群。SQLite 仅用于内部任务和当前创作状态，不增加面向用户的作品库。

### 4.2 数据流

```text
输入 → 文本模型生成三版歌词 → 手动编辑
→ 后端保存此次歌词和输入的快照，创建任务
→ worker 请求 AI 音乐规划
→ 校验规划 → 规则引擎生成音符与和弦
→ 校验乐谱 → MIDI → WAV → MP3
→ 校验实际时长 → 标记成功 → 前端试听、下载
```

AI 只提出可执行的音乐方向：速度、调式、段落小节数、和弦模板、节奏模板、主副歌的变化。规则引擎掌握具体音符和伴奏。模型只能选择已有模板 ID，不能凭空返回无法识别的模板。

AI 规划无效时，最多修复一次，再回退到该风格的默认规划。用户界面仍只返回一版音乐。歌词生成失败时直接提示重试，不悄悄用无关歌词替代。

### 4.3 数据结构草图

```text
MusicPlan {
  schemaVersion: 1,
  bpm: 100,
  meter: [4, 4],
  key: "C", mode: "major",
  sections: [
    {type: "verse", bars: 8, chordPatternId: "pop_a", rhythmPatternId: "sparse"},
    {type: "chorus", bars: 12, chordPatternId: "pop_b", rhythmPatternId: "hook"},
    {type: "outro", bars: 4, chordPatternId: "ending_a", rhythmPatternId: "ending"}
  ],
  melodyRange: [60, 79],
  chorusLiftSemitones: 3,
  seed: 12345
}
```

上述数字仅为结构示例，不是每首固定配置。升高副歌音区后也必须限制音域，不能直接把所有音机械加三。

4/4 拍、24 小节、100 BPM 时，乐谱长度为 `24×4×60÷100＝57.6 秒`。再加约 2 秒钢琴尾音，成品接近 60 秒。程序根据 BPM 和歌词分句调整整小节数，并将尾音纳入 45～75 秒限制。

### 4.4 优缺点与取舍

- 优点：音乐方向能受情绪和故事影响，具体音符仍可检查；AI 输出短，便于控制调用开销；后续修改规则不必重做页面。
- 缺点：AI 规划本身不能保证旋律动听；仍需人工试听和音乐规则调试；前后端两种语言会增加一点维护成本。
- 适用：当前首版的最佳折中。先把音乐结果做到稳定可听，再丰富动机和节奏规则。

### 4.5 大白话解释

AI 像音乐指导，说“这段安静一点，副歌亮一点”；程序像钢琴手，按可靠规则把具体音符弹出来。指导负责方向，钢琴手负责不乱拍、不超时。

## 5. 方案三：AI 直接生成音符

### 5.1 技术选型

沿用方案二的 React、FastAPI、Pydantic、SQLite、mido、FluidSynth 和 FFmpeg。差别是用文本模型直接输出完整的音符事件与和弦，不让规则引擎负责主要旋律创作。

模型输出包含段落、音高、开始位置、持续时间、力度，以及歌词行对应关系。选择服务时要确认结构化输出能力、输出长度限制和响应成本，不绑定一个具体模型。

### 5.2 数据流

```text
最终歌词与输入快照 → 文本模型输出完整乐谱 JSON
→ 格式与音乐约束校验
→ 无效时最多修复一次；仍无效则任务失败
→ MIDI → WAV → MP3 → 时长检查 → 试听、下载
```

首版一次生成全曲，避免分别生成主歌、副歌后调性或主题衔接不一致。接近输出上限时应压缩音符字段或换服务，不能把截断的 JSON 当作正常乐谱。

### 5.3 数据结构草图

使用第 6 节的 `Score` 与 `NoteEvent`，另记录 `modelId`、`promptVersion`、`repairCount`。模型输出要有明确的段落与歌词行标识，不能只返回一串音符。

### 5.4 优缺点与取舍

- 优点：音乐描述更自由，容易试验不同构思；初期可以少写一部分作曲规则。
- 缺点：长输出与修复可能抵消节省的成本；可能产生机械节奏、无意义重复、错位；JSON 合法不代表音乐好听；更换模型后结果可能明显变化。
- 适用：研究性试验，或已经听过目标文本模型的 MIDI 输出并确认效果。当前不建议作为默认路线。

### 5.5 大白话解释

让 AI 直接交一整份乐谱，程序照着弹。问题是它可能把格式写对了，却写出不好听的曲子；电脑能检查“每小节有没有数够拍子”，不能靠这个判断“副歌抓不抓耳”。

## 6. 共用数据结构与接口

### 6.1 数据结构

```text
Project {
  id, revision,
  input: {themeId, emotionId, styleId, story},
  lyricVariants: [{id, approach, text}],
  selectedVariantId, editedLyrics,
  currentAudioJobId, updatedAt
}

GenerationJob {
  id, projectId, requestId,
  sourceRevision,
  inputSnapshot, lyricsSnapshot,
  status: queued | running | succeeded | failed,
  stage, errorCode,
  composerVersion, promptVersion, soundfontVersion,
  seed, scorePath, midiPath, audioPath, durationSeconds,
  createdAt, finishedAt
}

Score {
  schemaVersion, ppq: 480, bpm, meter: [4,4],
  key, mode,
  sections: [{id, type, startTick, durationTicks}],
  lyricLines: [{id, text, sectionId}],
  tracks: [{role: melody | accompaniment, program, notes}]
}

NoteEvent {
  pitch: 60,
  startTick: 0,
  durationTicks: 480,
  velocity: 80,
  lyricLineId: "line_1",
  charStart: 0,
  charEnd: 1
}
```

`pitch: 60` 表示中央 C；`ppq: 480` 表示一拍分成 480 份。音符使用整数 tick，直到渲染边界才换算成秒：`秒＝tick÷480×60÷BPM`。伴奏音符不必携带歌词字段；歌词范围采用清洗标点后的 Unicode 字符索引，半开区间 `[charStart,charEnd)`。

不是每个汉字必须只有一个音符：可以一字多音，也可以在句尾留空拍。首版中文数字、英文片段的字数不等于实际音节数，应设定明确的计数规则；需要准确演唱适配时再扩展分词和读音处理。

### 6.2 最小接口

| 接口 | 用途 |
|---|---|
| `POST /api/lyrics` | 提交创作信息，返回三版歌词 |
| `POST /api/music-jobs` | 提交最新歌词与输入快照，返回任务 ID |
| `GET /api/music-jobs/{id}` | 查询状态、错误或成功后的音频地址 |
| `GET /api/music-jobs/{id}/audio` | 播放 MP3，支持 Range 请求和进度拖动 |
| `GET /api/music-jobs/{id}/download` | 下载同一份 MP3，设置下载响应头 |

重新生成使用同一个任务创建接口，创建新的任务 ID 和随机种子。前端查询任务状态即可，不需要增加实时推送系统。

### 6.3 任务与文件处理

- 网页请求负责提交任务，worker 负责执行；任务结果写入 SQLite。
- 每个任务使用独立目录，不共用 `output.mp3`。MP3 完成且检查通过后，原子更新为成功。
- 前端保留上一次成功音频；新任务成功且仍是当前等待的任务时，才替换播放器。
- worker 异常退出后，下次启动将遗留的 running 任务标记失败并允许重试，首版不做复杂自动恢复。
- 服务商 API 密钥只保存在后端环境变量；数据库、任务文件不存密钥。
- 音频、MIDI、乐谱为内部产物；磁盘空间需有配置化清理机制，不能删除当前正在使用的音频。

## 7. 推荐方案的作曲规则

1. **歌词分句**：识别主歌、副歌标题，以非空行组织乐句。用户手动编辑破坏标题时，提示补齐，不能猜错结构后继续生成。
2. **安排时长**：目标接近 60 秒，在允许的 BPM 范围内分配整小节，为尾音留余量。
3. **分配节奏**：按字数、句长安排音符及停顿。歌词过长导致明显不适合 75 秒时，提示用户缩短，不自动删词，也不强行塞成极快节奏。
4. **生成旋律**：强拍倾向和弦音，以级进和短动机为主；主歌与副歌共享部分动机，副歌作可辨识变化。
5. **生成伴奏**：同一时间轴上，使用低音与和弦或分解和弦；伴奏音区、力度避开主旋律。
6. **自然结束**：用稳定的和声和旋律收束，允许钢琴尾音衰减；不靠硬截断达到时长。
7. **说唱处理**：主要表现歌词节奏、简单动机与和声，不要求每字对应旋律音高。

这些是待验证的实现规则，不是现成库能自动保证的能力。尤其“记忆点”“好听”“情绪合适”要人工试听，不能只通过自动校验宣布达标。

## 8. 实现顺序与验证

1. 先做独立音乐管线：用手写乐谱 JSON 生成 MIDI、WAV、MP3，验证旋律和伴奏对齐、时长和下载文件可播放。
2. 用代表性歌词验证规则作曲：短句、长句、主副歌切换及说唱；确认自然结尾和副歌变化。
3. 接入三版歌词与手动编辑，再接 AI 音乐规划，比较它是否比默认规则有可听出的改善。
4. 接页面和任务状态，验证失败重试、重复点击、输入变更、旧任务晚返回、服务重启及音频拖动。

自动检查包括音符音高 0～127、时值为正、位置不超段落、旋律无非预期重叠、伴奏允许和弦重叠、主副歌均存在、成品 45～75 秒且非空。听感与歌词适配另外人工试听、必要时试唱。

没有实测前，不承诺具体生成秒数、每首费用或商业歌曲级质量。方案二开销主要来自两类文本请求、CPU 音频渲染和文件存储；重新生成也要计入成本。若在电脑上自测，避免购买持续在线服务器。

## 9. 以后自己改代码最容易踩的坑

| 容易改错的地方 | 后果 | 建议 |
|---|---|---|
| 混用秒、拍、小节、MIDI tick | 速度不对、音符错位、长度翻倍 | 内部统一 tick，只在一个模块转换 |
| 改 BPM 却不重算段落长度 | 时长超限，或者乐句太短 | BPM、小节数、尾音一起校验 |
| MIDI 文件要求相对时间，却写成绝对时间 | 后面的音符越来越晚 | 排序事件后，把绝对 tick 转为 delta tick；同位置先处理 note-off |
| 手动修改歌词后仍用旧缓存 | 音乐与页面歌词不对应 | 每次任务保存最新输入快照，记录 revision |
| 老任务比新任务晚完成 | 旧音乐覆盖新音乐 | 播放器只接受当前等待任务的成功结果 |
| 重新生成复用种子或缓存 | 多次点击听到同一首 | 新任务换种子；缓存键含歌词、输入、版本与种子 |
| 直接将模型 JSON 当作可信乐谱 | 漏段、越界、无效节奏 | 格式检查加音乐约束；有限修复，失败明确提示 |
| 用户把歌词写得很长 | 硬塞字、无停顿、不适合演唱 | 给出缩短提示；不偷偷改歌词 |
| 合成器当钢琴，或 SF2 音源丢失 | 听起来像电子提示音，或完全无声 | 固定钢琴音源，启动时检查路径与加载情况 |
| 试听与导出分别用两套渲染 | 下载和试听效果不同 | 两者使用同一 MP3 文件 |
| 音轨音量直接相加 | 爆音、失真、伴奏盖住主旋律 | 分轨设定音量，检查峰值，保留余量 |
| 部署到不支持本地程序的函数环境 | FluidSynth/FFmpeg 无法执行，任务超时 | 本地进程或支持系统依赖的服务器运行 |
| FastAPI 请求中同步执行重任务 | 页面卡住，其他请求被堵塞 | 交给独立 worker；同机 CPU 资源仍需限制 |
| 文件名或用户文本拼成 shell 命令 | 路径错误或命令注入 | 以参数数组启动进程，不启用 shell；用任务 ID 命名 |
| 改预设显示名称，破坏已有数据 | 旧数据无法找到风格规则 | 存稳定 ID，中文名称仅用于展示 |
| 更新库、提示词或规则不记录版本 | 同样输入突然效果变了，难排查 | 锁定依赖，保存规则、提示词、音源版本及种子 |

文本模型有随机性，单靠保存 seed 无法保证跨服务、跨版本完全复现。因此保留最终乐谱和音频，才是恢复同一结果的可靠方式。

音源文件的授权与程序库授权是两回事。使用可用于预期用途的 SF2/采样，不因渲染工具开源就默认所有音源都可分发。

## 10. 官方资料与依据

以下是技术能力参考；方案设计、成本取舍和推荐顺序为本项目的工程判断。

- [FluidSynth 官方资料](https://www.fluidsynth.org/)：支持 SoundFont 与 MIDI 播放，作为 MIDI 到声音的渲染工具。无需图形界面。
- [Tone.js 官方资料](https://tonejs.github.io/)：支持浏览器音乐调度与采样器，但浏览器音频启动需要用户交互。本项目优先统一播放成品音频，减少两套播放路径。
- [FastAPI 后台任务说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)：耗时计算需考虑独立执行方式。本项目自测阶段采用单独 worker，不直接把重渲染塞进请求处理。
- [mido 文档](https://mido.readthedocs.io/en/stable/files/midi.html)、[Tonal 项目](https://github.com/tonaljs/tonal)、[FFmpeg 文档](https://ffmpeg.org/ffmpeg.html)：开发时核对所锁定版本的时间单位、接口和编码能力。

最终建议：选方案二，以方案一的规则引擎作为稳定基础。先证明钢琴小样对你的目标用户有用，再投入更复杂的音乐生成。
